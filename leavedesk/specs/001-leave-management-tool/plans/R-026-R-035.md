# Plan 03: R26 email notifications + R35 in-app notifications (infrastructure)

Phase P1. Depends on: plan 01 (audit, privacy filter conventions). Blocks: 04 (invite/reset emails), and every plan that raises an event.

Platform: the outbox drain schedule uses the reusable `job.yml` from plan 00 (`R-platform.md`); this plan adds only the job module and its caller.

## Requirements and acceptance criteria

- **R26**: one email per event to the right recipient (created, approved, rejected, cancelled by employee, cancelled by HR, approved on behalf, invite, reset); content has date range and link, **no Sick type, never the note**, rejection reason only to the employee; `EMAIL_BACKEND=mock` stores rendered mail in `email_outbox` as `mocked`; SendGrid failure keeps mail in the outbox with back-off (1 min, 5 min, 30 min, 2 h, 12 h; 5 attempts → `failed`, visible to HR); mock in production → app refuses to start.
- **R35**: every R26 event also creates an in-app notification (bell, unread count); opening marks read and links; another user's notifications → 403; same privacy rules; invite is email-only.

**Scoping decision for independent delivery:** this plan delivers the machinery, the template/privacy-filter framework, the failed-email HR endpoints, and the *invite* and *reset* templates (needed by plan 04). Templates and wiring for request events ship with the plan that creates the event (10, 12, 13, 14, 15, 16). A conformance test listing all eight events is added here with the unwired events marked pending; the last event plan removes the last pending marker. Flag: the full "each event → right recipient" criterion of R26 is only provable once plans 10–15 land.

## Steps

1. Tests first (privacy filter, back-off schedule, startup guard, 403 on others' notifications).
2. `email_outbox` and `notification` tables (RLS, indexes from §5.3).
3. `EmailSender` interface; `MockEmailSender` writes `mocked`; `SendGridSender` maps provider status to `last_error` (status code only).
4. Single `emit(event, recipient, request_ref)` service that writes outbox + notification in the caller's transaction, with `dedupe_key`.
5. Privacy filter: builds payload from an allow-list (dates, link, generic "Off"/"leave"); a Sick request is rendered as "leave" for everyone but the owner and HR.
6. Drain job with back-off and in-process background task every minute.
7. HR endpoints: list failed, manual retry (audited).
8. Notifications API and bell UI.
9. Startup guard: mock + production → exit non-zero.

Constraints for callers:
- `emit()` requires `occurrence` for invite and reset (use the token id), or a repeat would be deduplicated away. Request events default to one email per event, recipient and request; pass `occurrence` (e.g. the request `version`) if the same event can repeat.
- `emit()` runs in the caller's transaction; the caller commits.
- Pass `rejection_reason` only for the rejected event, addressed to the request owner.

Open concerns:
- **Retry count:** "5 attempts" with five delays leaves the 12 h step unused (5th failure marks `failed`). Confirm 5 attempts vs 5 retries (6 sends).
- **Tokens in the outbox:** invite and reset links sit in `email_outbox.body` and `payload` until purged. Plan 19's `purge` should blank or delete sent rows for those templates.
- **At-least-once delivery:** a crash between a successful send and the commit resends the mail. Accepted; add a provider idempotency key if duplicates matter.
- **In-process drain on FastAPI Cloud** is unproven (A-28); every worker runs the loop (safe, rows are locked with `SKIP LOCKED`).
- **A-14:** recipients for HR-queue events are still undefined; `emit()` takes the recipient from the caller.
- **403 vs 404:** another user's notification returns 403, a missing one 404, so existence is observable (UUIDs, spec requires 403).
- `GET /hr/email-outbox?status=` accepts only `failed`; the parameter is unused until another status is needed.
