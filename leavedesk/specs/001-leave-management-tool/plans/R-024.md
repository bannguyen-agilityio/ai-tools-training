# Plan 08: R24 starting balances by hand

Phase P1. Depends on: 05 (ledger), 07 (employees). Blocks: 21; needed before go-live (C-9).

## Requirements and acceptance criteria

- **R24**: HR enters opening Annual, carried days with expiry date, and Sick as ledger entries with actor and time; value outside 0–40 refused; confirmation summary before saving; changes are new adjustment entries with a required reason; originals never overwritten.
- C-9 safeguards: printable "balances at launch" list.

Endpoints #23 (`GET /hr/balances`), #24, #25 (preview), #26 (create entry).

## Files

Create: `app/modules/balances/hr_router.py`, `hr_service.py`, `hr_schemas.py`; `frontend/src/features/hr/balances/{BalanceList,EntryForm,ConfirmSummary,PrintView}.tsx`; `tests/balances/test_hr_entries.py`.
Modify: `app/modules/balances/repository.py` (bulk list).
Delete: none.

## Steps

1. Tests first: range, preview-writes-nothing, adjustment-needs-reason, 403 matrix, audit.
2. Preview endpoint returns the summary (employee, type, kind, days, expiry, resulting balance) without writing.
3. Create endpoint: kinds `opening`, `carry_over`, `adjustment`; `source=manual`; audit; `corrects_entry_id` for adjustments.
4. Ledger view per employee, with entries newest first.
5. All-employee balance list and a print stylesheet (the "balances at launch" list).
6. UI: entry form → summary dialog → save.

## Risks and dependencies

- A-18: does 0–40 bound signed adjustments (e.g. −2)? Can opening Sick be entered? Allowed `expires_on` range for carry-over? Spec says only "outside 0–40". Implement 0–40 for opening/carry-over, and ask before bounding adjustments.
- Typos are the largest accuracy risk (C-9): keep the confirmation step mandatory in API (preview token) or UI only? Spec is silent; decide with the product owner.
- 250 manual entries in days: usability of the form (keyboard flow) matters for the schedule.

## Open items (after PR #65)

- **[Assumption] A-18** (adjustment bound −40..40, opening Sick allowed, carry-over `expires_on` in the entry's leave year) is written into spec R24 but not confirmed by the product owner. Revisit before go-live (C-9).
- Confirmation is UI-only; the API does not require a preview token before create. Decide with the product owner whether to enforce it server-side.
- Backend tests in `tests/modules/balances/test_hr_entries.py` and the full pytest suite were not run in the authoring environment (no Docker/Postgres); CI must show them green.
- Playwright e2e and the manual R31 AA checklist for the new screen were not run; do on staging.
- Keyboard flow for entering ~250 employees is one employee at a time through list, form, summary; revisit if too slow.
- Code review, not fixed: (a) a negative adjustment can take `available` below zero and the preview does not warn (slice 09 balance display can add the warning); (b) a manual `carry_over` (0–40) is not capped at 6 and is not linked to the 1 Jan rollover job's carry, so both could stack in 2027 (decide cap with the product owner before 1 Jan 2027); (c) `leave_year` defaults to today's year and the form has no year picker, so prior or next year entries are not possible; (d) adjustments have no idempotency key, so a retried POST appends a duplicate (the Save button is disabled while pending); (e) `all_balances` loads the year's ledger in one query, fine for ~250 staff.
- Fixed from review: `1e999` returned 500 (now 422); a second manual opening or carry-over for the same employee, type and year is 409; `corrects_entry_id` must match employee, type and year.
