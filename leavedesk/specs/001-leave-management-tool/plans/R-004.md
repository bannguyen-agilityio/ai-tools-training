# Plan 16: R4 deactivation

Phase P1. Depends on: 07 (employees), 12 (cancel service), 04 (sessions). Blocks: none.

## Requirements and acceptance criteria

- **R4**: HR deactivates an employee → their next request is refused and sessions deleted; history stays; their Pending requests are cancelled and their manager told.
- R34 coupling: leave history of a deactivated employee is kept and HR-only (see plan 19).

Endpoint #19 (`POST /hr/employees/{id}/deactivate`).

## Files

Create: `app/modules/employees/deactivate.py`; template `cancelled_on_deactivation` (to the manager); confirmation dialog in HR Employees UI; `tests/employees/test_deactivate.py`.
Modify: `app/modules/identity/dependencies.py` (reject inactive users even with a stale session), `employees/router.py`.
Delete: none.

## Steps

1. Tests first: single-transaction behaviour, sessions gone, token reuse, authz.
2. One transaction: `is_active=false`, `deactivated_at`, delete sessions, cancel each Pending request (day rows inactive), audit each, outbox + notification to manager.
3. Auth dependency checks `is_active` on every request.
4. Block login/reset/invite for inactive users.
5. UI: confirm dialog naming the effects, default focus "Keep".

## Risks and dependencies

- A-11: Pending requests *assigned to* a deactivated manager, and deactivating HR admin, the deputy, or a manager with reports, are all unspecified. Implement only the specified path; refuse deactivation of HR admin/deputy with a clear error until answered, and flag in the PR.
- Partial failure must roll back everything.
- Approved future leave of the deactivated employee still reserves days; not addressed in the spec.
