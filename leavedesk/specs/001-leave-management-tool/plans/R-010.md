# Plan 09: R10 balance display and sufficiency check

Phase P1. Depends on: 05 (`compute_balance`), 06 (request/day tables). Blocks: 10.

## Requirements and acceptance criteria

- **R10**: Dashboard shows per type entitlement, carried (with expiry date), used (Approved), reserved (Pending) and available; Available = entitlement + carried − used − reserved; an Annual/Sick request that would go below zero is blocked, stating the shortfall; Unpaid never blocked.

Endpoint #8 (`GET /me/balances?year=`). The blocking criterion is delivered here as a reusable service function `ensure_sufficient(employee, type, requested_days_per_year)` with unit tests; plan 10 calls it from submit and adds the integration test. Flagged because R10's third criterion is only end-to-end provable in plan 10.

## Files

Create: `app/modules/balances/me_router.py`, `me_service.py`, `schemas.py` additions; `app/modules/balances/sufficiency.py`; `frontend/src/features/dashboard/{Dashboard,BalanceCard}.tsx`; `tests/balances/test_me_balances.py`.
Modify: `app/modules/balances/repository.py` (load entries and day rows per year).
Delete: none.

## Steps

1. Tests first: API response for fixtures, sufficiency boundary (exactly zero ok, −0.5 blocked), Unpaid unlimited, manager-cannot-see-reports check.
2. Repository loads ledger entries and active day rows.
3. Service builds the response from `compute_balance` only (no extra arithmetic).
4. `ensure_sufficient` with per-year deduction (cross-year request checks each year; carried-first).
5. Dashboard UI with carry-over expiry date, upcoming leave placeholder (data from plan 10), "Request leave" button.
6. `GET /me/balances` returns only the caller's data; `year` validated.

## Risks and dependencies

- A-24: spec shows "carried-over (with its expiry date)" as one value; confirm single block per type/year.
- Reserved/used depend on `is_active` flags maintained by plans 10–15; add invariant test there.
- Managers must not see reports' balances (Q11): no endpoint here accepts an employee id.
